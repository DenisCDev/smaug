# Sentry in Next.js — activation steps

Applies only if the project uses `@sentry/nextjs` (declared in `package.json`). If it does not,
delete the generated files below: adding Sentry is a new dependency and a project decision, not a
default of `smugan init`.

The files generated by `smugan init` (`instrumentation.ts`, `instrumentation-client.ts`,
`sentry.server.config.ts`, `sentry.edge.config.ts`) follow the current format of the official docs
(https://docs.sentry.io/platforms/javascript/guides/nextjs/manual-setup/). Still to do:

1. **Dependency**: confirm `@sentry/nextjs` is declared and lockfile-resolved, at a version the
   docs above cover.
2. **next.config**: wrap it with `withSentryConfig`:
   ```ts
   import { withSentryConfig } from '@sentry/nextjs';
   export default withSentryConfig(nextConfig, { org: '<org>', project: '<project>' });
   ```
3. **Env vars** (per environment — Production/Preview, e.g. on Vercel):
   - `NEXT_PUBLIC_SENTRY_DSN` (client) and `SENTRY_DSN` (server/edge) — the DSN is not a secret,
     but keep it in env to separate projects.
4. **Source maps** (readable stack traces in production): set `SENTRY_AUTH_TOKEN` in the build
   environment — `withSentryConfig` uploads the source maps during the build. On Vercel, without a
   manual token: the Sentry↔Vercel integration
   (https://docs.sentry.io/organization/integrations/deployment/vercel/) creates
   `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN` and the DSN automatically.
5. **Verify**: throw a deliberate error in a route handler and confirm the event in Sentry
   before considering observability done.
